# Бекап избранных стикеров: экспорт кнопкой, импорт тапом

Дата: 2026-08-21
Статус: согласовано, готово к плану реализации

## Зачем

Избранное плагина живёт только в `stickers.json` внутри приватного каталога приложения. Переустановка, очистка данных или переход на другое устройство уничтожают его без следа: на сервере лежат только первые `maxFaveStickersCount` стикеров, всё сверх лимита существует ровно в одном экземпляре. Пользователю нужен способ вынести подборку наружу и вернуть обратно.

В ветке `Добавить-возможность-делать-и-восстанавливать-бекапы` (PR #10) это уже написано, но экспорт там запускается командой в поле ввода — из-за чего плагин перехватывает каждое исходящее сообщение (issue #4). Эта спека описывает замену: экспорт кнопкой в настройках плагина, импорт тапом по файлу.

## Что берём из PR #10

- **Расширение `.stickers`** — однозначно опознаётся при тапе, не конфликтует с чужими вложениями.
- **Перехват `AndroidUtilities.openForView` по имени, а не по сигнатуре.** Набор перегрузок в сборках отличается; привязка к одной сигнатуре молча промахнётся. Это тот же урок, что закрыт в `fix/silent-failures` для `getRecentStickers`.
- **Обработка недокачанного файла** — тап по документу, который ещё не скачан, обязан сказать об этом, а не молчать.

## Что выбрасываем

- Команду в поле ввода и `on_send_message_hook` целиком — вместе с issue #4.
- Запись в публичный `Downloads` через MediaStore и `ACTION_SEND`. Вместо них `file_utils.write_file` в кеш и `client_utils.send_document` — три строки вместо сотни, без работы с разрешениями и интентами.

## Формат файла

Версия одна: `1`. Импорт принимает только её, на любой другой отказывается с сообщением, что файл новее плагина. Это защита от ситуации, когда будущий формат молча испортит базу старому плагину.

### Экспорт текущего аккаунта

```json
{"version": 1, "stickers": [
  {"id": 123, "access_hash": 456, "dc_id": 2, "mime_type": "image/webp", "sticker_set_id": 789}
]}
```

Плоский список в порядке панели — новые сверху. Идентификаторов аккаунта в файле нет вовсе: такой файл можно отправить другому человеку, чтобы поделиться подборкой.

### Экспорт всех аккаунтов

```json
{"version": 1, "accounts": {"501713909": ["123"]}, "stickers": {"123": {"id": 123, "...": "..."}}}
```

Слепок базы плюс версия. Содержит user id — предназначен только себе.

### Различение

По наличию ключа `accounts`. Список ложится в тот аккаунт, где нажали «Импорт»; слепок раскладывается по id аккаунтов из файла. Аккаунты из слепка, в которые пользователь сейчас не залогинен, всё равно попадают в базу — они пригодятся, когда он войдёт.

Имена файлов: `favorites-<ГГГГ-ММ-ДД>.stickers` и `favorites-all-<ГГГГ-ММ-ДД>.stickers`.

## Части

Плагин обязан оставаться одним файлом: `.plugin` — это один `.py`, и релизный workflow копирует именно его. Поэтому разделение логическое, а не по модулям.

### StickersDB — четыре новых метода

Данные принадлежат ей, вскрывать приватный словарь снаружи нельзя.

```
export_account(account) -> dict          # {"version": 1, "stickers": [...]}
export_all() -> dict                     # слепок базы
import_account(data, account, replace) -> ImportResult
import_all(data, replace) -> ImportResult
```

`ImportResult` — сколько записей применено и сколько пропущено как непригодные.

Точные значения `replace`:

- **Слияние** (`replace=False`) — добавляются недостающие, ничего не удаляется. Повторный импорт того же файла не меняет ничего.
- **Замена** (`replace=True`) — список аккаунта становится ровно тем, что в файле, вместе с порядком. Для слепка замена применяется **только к тем аккаунтам, которые есть в файле**; аккаунты, которых в файле нет, не трогаются вовсе. После замены записи, на которые больше не ссылается ни один аккаунт, удаляются из общего словаря — по тому же правилу, что в `remove_sticker`.

Все четыре — чистый Python без обращений к Java, то есть полностью покрываются стендом.

### Функции работы с файлом

- `backup_filename(scope) -> str`
- `parse_backup(text) -> dict` — разбор, проверка версии и формы, понятная ошибка на каждый вид брака
- `detect_scope(data) -> "account" | "all"`

### MyPlugin.create_settings()

```
Header("Бекап избранного")
Text("Экспорт текущего аккаунта", subtext="<N> стикеров → в «Избранное»", on_click=…)
Text("Экспорт всех аккаунтов",   subtext="<M> стикеров, <K> аккаунта",   on_click=…)
Divider(text="Чтобы восстановить, откройте файл .stickers в любом чате и подтвердите импорт")
```

Счётчики читаются из базы при построении экрана — после кеширования разбора это бесплатно. `Divider` решает обнаружимость: импорт не кнопка, и без подсказки о нём никто не догадается.

### ImportBackupHook

Вешается на все перегрузки `AndroidUtilities.openForView`. Опознаёт наш файл по расширению — либо по `getAbsolutePath()` у `File`, либо по имени документа у `MessageObject`. Только после успешного опознания гасит штатное открытие через `setResult(False)`.

## Потоки

**Экспорт.** Нажатие → `StickersDB.export_*` → `json.dumps` → `file_utils.write_file` в `get_cache_dir()` → `client_utils.send_document(мой_user_id, путь)` → плашка «Отправлено в Избранное». `send_document` ждёт числовой peer, а база ключуется строкой — приведение делается явно, чтобы не повторить историю с `jint`. Файл живёт в кеше секунды и не мусорит в пользовательских каталогах.

**Импорт.** Тап → хук узнаёт расширение → `setResult(False)` → чтение и разбор → диалог с числом стикеров и выбором «Добавить» / «Заменить» → применение → сброс кеша базы → `__notify_favorites_changed()` → плашка «Импортировано N, пропущено M».

Перерисовка панели достаётся импорту бесплатно: механизм уже сделан в `fix/db-hardening`.

## Отказы

Колбэк настроек выполняется в Java-UI, и исключение из него, вероятнее всего, проглатывается так же молча, как в хуках. Поэтому каждый обработчик обёрнут, и **каждая ветка отказа заканчивается плашкой**, а не только записью в лог.

| Ситуация | Поведение |
|---|---|
| Экспорт при пустой базе | Отказ с «нечего экспортировать», пустой файл не отправляется |
| Ошибка записи файла | Плашка с причиной, строка в лог |
| Ошибка отправки | Плашка с причиной, файл остаётся в кеше |
| Тап по недокачанному файлу | «Дождитесь загрузки», штатное открытие не запускается |
| Битый JSON, чужая форма, незнакомая версия | Плашка со своей причиной на каждый случай |
| Запись без обязательных полей | Пропускается поимённо в лог, в итоге «импортировано N, пропущено M» |

### Замена — единственная разрушительная операция плагина

Перед применением режима «Заменить» текущее состояние **всей базы** автоматически сохраняется слепком в кеш, путь пишется в лог. Кеш — приватный каталог, пользователь оттуда ничего не достанет, поэтому слепок тем же путём, что и обычный экспорт, уходит в «Избранное» через `send_document`. Стоит несколько килобайт, а спасает от потери подборки, которой нет на сервере.

## Риск, который надо держать в голове

Хук на `openForView` висит на **всех** открываемых файлах. Ошибка в опознании «наш/не наш» ломает открытие любого вложения в мессенджере. Поэтому `setResult(False)` вызывается строго после проверки имени, и на это заводится отдельный тест: хук получает pdf, jpg, файл без имени и `None` — и обязан не тронуть результат ни в одном случае.

## Тесты

На стенде (`tests/test_plugin.py`, Java подменена стабами):

- форма и порядок обоих форматов экспорта;
- круговой рейс: экспорт → импорт в пустую базу → совпадение состава и порядка;
- импорт файла одного аккаунта в **другой** аккаунт;
- слияние против замены;
- повторный импорт того же файла в режиме слияния ничего не меняет;
- битая запись пропущена и посчитана;
- незнакомая версия отклонена;
- `detect_scope` на обоих форматах;
- хук не трогает чужие файлы;
- замена делает страховочный слепок.

Только на устройстве:

- `send_document` реально доходит до «Избранного»;
- диалог подтверждения рисуется и обе кнопки работают;
- `openForView` перехватывается во всех перегрузках конкретной сборки;
- тап по обычному вложению по-прежнему открывает его.
